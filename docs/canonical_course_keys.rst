Canonical course keys
=====================

The same course can be reached with differently cased course keys, for instance
``course-v1:Org+IBPC+2025_T1`` and ``course-v1:Org+iBPC+2025_T1``. MySQL matches them
case-insensitively, but edx-platform does not consider them equal. An enrollment keeps the
casing of the URL used to enroll, so the course links generated from it can have the wrong
casing. The course block structure is shared by all the casings but is only valid for one of
them, so the Learning MFE API calls of those links fail and the learner sees an error page.

What it does
------------

The casing stored in the course overview (the canonical one) is used instead, without changing
any data:

* ``CanonicalCourseKeyMiddleware``, in the LMS and in Studio, replaces the course and block keys
  of the request URL path by the canonical ones, keeping the branch and the version of the keys.
  Course keys in query strings or request bodies are not replaced, and neither are the keys after
  the first three of a path, to bound the database lookups that a single request can trigger.
* ``CourseHomeUrlCanonicalCourseKey``, a pipeline step of the
  ``org.openedx.learning.course.homepage.url.creation.started.v1`` filter, makes the course home
  URLs generated by the platform use the canonical key (learner dashboard, emails, redirect after
  enrolling).

Both are registered by the plugin settings, so the filter step must not be added to
``OPEN_EDX_FILTERS_CONFIG`` through the Tutor patches too. The canonical key lookup is cached.

Configuration
-------------

``NAU_CANONICAL_COURSE_KEYS_ENABLED``
    Default: ``True``. Set it to ``False``, for instance in the env tokens, to disable it.
